`merge-ops.json` shape:
```json

  "merge": [
    { "keep": "T-001", "drop": "T-014", "reason": "same evaluator contract definition" }
  ],
  "add_edges": [
    { "from": "T-001", "to": "T-009", "type": "blocks", "reason": "contract blocks evaluator implementation" }
  ],
  "add_dependencies": [
    { "task": "T-009", "depends_on": "T-001", "reason": "implementation needs defined contract" }
  ],
  "update_tasks": [
    {
      "id": "T-009",
      "target_list": "blocked",
      "add_labels": ["blocked", "needs-decision"],

    }
  ]
}
```

Operation semantics:
- Use `merge` only for true duplicates. `keep` survives; `drop` is removed; array fields are unioned by the script.
- Use `add_dependencies` when a task cannot proceed until another task is complete. The script also emits a `blocks` edge.
- Use `add_edges` for useful relationships that should not alter the task's dependency list, or for explicit edge-only relationships.
- Use `update_tasks` for small semantic corrections: target list, labels, blockers, title, type, priority, description, confidence, or array additions/sets.
- Do not use operations to expand scope beyond analyzer outputs.

## Granularity Rules (MERGER — CRITICAL)

### DO NOT FUSE independent tasks

The analyzer outputs ~50 candidate tasks. The merger must produce a plan close to that count after true dedup only.

Forbidden fusions:
- **NEVER** fuse CLI commands into one card. Each distinct command group gets its own card:
  — init command (separate)
  — intention create/list/evaluate (separate or grouped as "intention CRUD", NOT mixed with task commands)  
  — task list/show (separate)
  — check list/gap list (separate)
- **NEVER** fuse evaluator components:
  — repository context inspector (separate from stub evaluator)
  — stub evaluator (separate from context inspector)
  — Evaluator output validation (separate)
  — Evaluator 8-step pipeline core (separate)
- **NEVER** fuse gap generator and task generator — these are distinct pipeline stages
- **NEVER** fuse ambiguous intention handler into task generator — it is a separate concern
- **NEVER** fuse acceptance tests into one giant card — split E2E smoke tests from unit/validation tests
- **NEVER** fuse documentation card with implementation cards

Allowed fusion (dedup only):
- Same core deliverable described in 2-3 shards → keep ONE card, merge source references
- Example: Shard1 "Implement storage layer" + Shard2 "Implement SQLite storage" = ONE storage card
- Example: Shard3 "Define data types" + Shard4 "Define data types as TypeScript" = ONE types card

Dedup criteria — two tasks are TRUE duplicates ONLY when:
1. They propose the EXACT same core deliverable (same files / same module boundary / same single responsibility)
2. They share the same source section(s) in the spec
3. Their acceptance criteria overlap >80%
4. Either task alone satisfies the spec requirement fully

If tasks 1-3 pass but criteria differ → merge acceptance criteria but keep separate IDs.
If all 4 fail → they are DIFFERENT tasks. Keep separate.

### Quantity guard

- Expected final task count: 50%+ of total analyzer output (after removing true dedups only)
- If final count < 50% of analyzer total → STOP and re-review. You are over-merging.
- Report in `warnings`: expected count vs actual count and reason for any significant reduction.

Dependency edge semantics:
- Use `{ "from": "T-001", "to": "T-002", "type": "blocks" }` when `T-001` blocks `T-002`.
- For each task dependency `T-002.dependencies = ["T-001"]`, include the matching edge `{ "from": "T-001", "to": "T-002", "type": "blocks" }`.
- Use `{ "from": "T-002", "to": "T-001", "type": "depends_on" }` only when expressing the dependent-to-dependency direction is clearer.
- Prefer `blocks` for definition tasks that unblock implementation work.
- Use `relates_to` only for non-blocking relationships that are useful to preserve.

## Validation Gate (MANDATORY)

After writing `.opencode/data/merged-task-plan.json`, you MUST validate the plan before considering your work complete.

Validation steps:

1. **T-xxx format**: Every `tasks_to_create[].local_id` must match `T-\d+` (e.g., T-001, T-042). No exceptions.

2. **Uniqueness**: No duplicate `local_id` values across all tasks.

3. **Dependency integrity**: Every value in `tasks_to_create[].dependencies` must reference an existing `T-xxx` ID from the plan.

3a. **Execution order integrity**: `tasks_to_create` should be topologically sorted so each dependency appears before the task that depends on it. If helper tooling later reorders cards, this still keeps the plan readable.

3b. **Actionability integrity**: Every non-definition task must include concrete `implementation_boundary`, non-empty `implementation_steps`, and a runnable `verification.command` with an expected result. If a task does not say where to edit and how to test, update it before validation.

4. **Edge integrity**: Every `dependency_edges[].from` and `dependency_edges[].to` must reference existing `T-xxx` IDs.

5. **No cycles**: Run a topological sort. If a cycle exists, break it by removing the weakest edge (lowest priority first).

6. **Array format**: `acceptance_criteria`, `implementation_notes`, `blockers`, `dependencies`, `labels`, `source_references` must ALL be arrays. Never strings.

7. **Source references**: Every task must have at least one entry in `source_references`.

8. **Field count**: The file must have EXACTLY four keys at the top level: `tasks_to_create`, `dependency_edges`, `cards_to_move`, `output_contract`. No extras.
9. **Board ID collision check**: Run `node .opencode/scripts/find-next-task-id.cjs`. If any proposed `local_id` already exists on the board, offset all IDs by the difference so the first new task starts at the returned `next_id`. This check is mandatory before calling the writer.

Run the validation script after writing:

```
node .opencode/scripts/validate-merged.mjs
```

If validation reports errors, fix them and re-run. The plan must pass all checks before you consider your work done.
